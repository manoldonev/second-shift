I read the two implicated scripts (`orchestrate-lean.sh`, `lean-gate.sh`) and the merge-boundary reader before writing this. One finding up front, because it reshapes several ACs: the ticket names two candidate mechanisms, and there is a third visible in the code that neither AC addresses.

## Decisions to settle before planning

1. **A third candidate mechanism exists, and if it's the real one the base advance is causally irrelevant.** `verdict_rc` (`orchestrate-lean.sh:607-611`) resolves the lane worktree via `lane_worktree` (`:533-542`) and returns **3** if no worktree is registered for the branch — without ever invoking the gate. The timeline has teardown removing the worktree at 21:43:24 and the REVIEW spawn at 21:45:03, one second after the BUILD spawn exited; a gate-less fail is exactly that fast. Under this mechanism neither the staleness base arm (which only runs before the *build* spawn, `:708`) nor milestone-4's patch-id arm ran at all, and note that merging #595 into `main` does **not** move `merge-base(origin/main, 8c8d5cb)`, so candidate 2 has no obvious way to fire either. The decision: if the pinned mechanism is "the verdict read cannot survive teardown," is the deliverable still the base-advance semantics of AC-1/AC-3/AC-4, or does the ticket become "verdict_rc must be answerable without a live worktree"? These are different builds, and the first one can land in full while the incident still recurs.

2. **Which layer is allowed to change: the spawn decision, the gate's milestone 4, or the merge boundary.** AC-1's "no re-stamp is required" cannot be satisfied by the scheduler alone — the re-stamp exists because milestone 4 (`lean-gate.sh:4416-4428`) and `lean-reconcile.sh:354-386` both recompute `reviewed_patch_id` and refuse the record. Loosening the scheduler costs at most a wasted review; loosening the merge boundary changes what a green merge-authorization gate asserts about reviewed content. Whether the merge-boundary reader is in scope is undecided and is the single biggest risk difference in the ticket.

3. **Whether AC-3's "cannot name a line ⇒ the verdict stands" governs every invalidation or only base-attributed ones.** Read literally against milestone 4's patch-id arm, an ordinary build fix push also cannot name a base-affected line — so the rule as written would let the verdict stand over content nobody reviewed. Someone has to draw the line between "the base moved and we are in doubt" and "the branch itself moved," including how the code establishes *which* of the two happened at a site that currently knows nothing about the base.

4. **What AC-2 means for non-approve verdicts.** rc=0 at an unmoved head already skips the review (`:819-822`). AC-2 says no REVIEW is spawned at an unmoved head "regardless of base movement" — if that includes rc=1 (needs-work), the lane must do something else instead (stop? spawn BUILD and refuse to review until the head moves?), and a build session that commits nothing would otherwise loop. Whether AC-2 is an approve-only rule or a verdict-agnostic one changes the control flow.

5. **Where the fact "a verdict was gate-confirmed against head H" is durably stored, and whether it is re-derived or attested.** AC-2 needs that fact to survive both teardown and the scheduler process. The `.claude/pipeline-state/583-*` receipts are gitignored (the ticket says so), the lane log is outside the repo, and the worktree is gone by the time the question is asked. The available durable source is the committed verdict record itself (`reviewed_head` / `reviewed_patch_id`) read from the branch — but that is a *declaration*, not a confirmation, and the lane's standing posture is that an attestation is not a gate.

6. **Whether the new comparison replaces `branch_patch_id` or is added beside it — and what happens to records already in flight.** `reviewed_patch_id` is a header key with four readers in lockstep (`lean-gate.sh`, `lean-reconcile.sh`, `lean-evidence.sh`, the consumer template `second-shift-delta-guard.sh`), a `capability-parity.tsv` row, a schema entry, and an *inheritance chain* that matches prior rounds by exact id equality (`lean-gate.sh:929`, `:980`; reconcile `:437`). Replacing the identity breaks chain walks over records already committed on in-flight branches; adding a second key costs guard mass under the earn-your-keep/guard-budget rules. Which way, and what the back-compat arm for pre-existing records is, is undecided.

7. **Where the "before" side of the comparison comes from.** AC-4 mechanizes `git diff ea299d6 8c8d5cb -- <f>` vs `git diff origin/main HEAD -- <f>` — the first needs the *pre-merge* merge-base, which after the base merge has to be recovered from history (first-parent walk, the reviewed_head's own branch point) or else recorded at review time as per-file digests in the verdict record. The merge-boundary reader in CI has only the PR's declared base and no runtime config, so a re-derivation strategy that works locally may not be computable there at all.

8. **Whether a base edit *adjacent to* a reviewed line counts as certainty or doubt.** The whole reason the id moved on #583 is that patch-id hashes context lines; hashing only `+`/`-` lines makes the identity blind to a base change in the surrounding context of a reviewed hunk. Under the operator constraint that is "doubt ⇒ stands," but it is worth stating explicitly, because it is the precise case where "your lines are byte-identical" and "your change still means something different" diverge.

9. **What normalization the per-file `+`/`-` comparison uses, and how the file set is allowed to change.** Renames, whitespace, a file the branch touched that the base *deleted*, a file that appears in the post-merge diff but not the pre-merge one, and the existing exclusions (`:(exclude)$VERDICT_REL`, and the render manifest for `render_patch_id`) all have to be settled — the nine-file example is the clean case and does not decide any of them.

10. **How faithfully AC-5's regression guard must reproduce the scheduler path.** A guard that exercises only the gate predicate would have passed on #583 under mechanism (1) while the lane still spawned the review; a guard that exercises `orchestrate-lean.sh`'s spawn decision needs `spawn` stubbed and a fabricated lane worktree plus teardown. Also undecided: which selftest file it lands in, and whether it goes into `selftest-slow-suites.tsv` — a slow-suite catalog row is deferred by the PR-mode mutation sweep and so gets graded by nothing.

11. **Whether a base *merge* into the lane branch is a supported lane operation at all.** The re-stamp cost only arises because `origin/main` was merged in (`5d6024e`); `git merge`/`rebase`/`reset` are deny-listed inside a build re-entry, and patch-id already survives a rebase by design (#372). If the intended remedy for a conflicting lane branch is "rebase, not merge," AC-1's whole cost class is out-of-band operator work rather than lane behaviour — and that changes whether this ticket is a semantics fix or a lane-procedure fix.

# Namespace conventions

Plugin content is addressed as `<plugin>:<name>`. Rules the extraction follows:

1. **Skills**: invoked as `dev-pipeline:run`, `review-toolkit:review-lead`, `intake-toolkit:plan-interview`, etc. **User-facing slash invocations are namespaced too**: `/dev-pipeline:run`, `/dev-pipeline:review`, `/intake-toolkit:intake`, `/audit-toolkit:audit`, `/second-shift:onboard`, `/second-shift:doctor`, `/second-shift:local-dev-refresh`. (Verified empirically: bare short forms like `/review` do NOT resolve for plugin skills once the same-named vendored copy is gone — "Unknown command". Docs and skill files must always show the qualified spelling.)
2. **Agents**: `.mjs` workflows and skill files reference agents by qualified name (`review-toolkit:security-reviewer`). Repo-local agents (config `reviewers.add`) are referenced bare — that's the disambiguation between roots.
3. **Cross-plugin dependencies are one-directional**: dev-pipeline → {review-toolkit, intake-toolkit, design-toolkit, audit-toolkit}. The four toolkits never reference dev-pipeline. Between toolkits exactly two arrows are sanctioned:
   - **intake-toolkit → review-toolkit**: the shared review protocol and review-toolkit's `intake-review.mjs`. The protocol's contract is the **Sub-Agent Trust Model**, canonical in `review-toolkit:review-lead` and cited by `intake-orchestrator` and `decomposition-reviewer`.
   - **review-toolkit → design-toolkit, optional**: qualified agent names only (`design-toolkit:…`). Everything degrades when design-toolkit is absent — review-lead's toolkit-absent degrade, and `check-model-tiers.sh` skips the `design-toolkit:` table rows.

   **Workflow scripts ship in review-toolkit**, which owns the reviewer and intake-review fan-out. Its `workflows/` holds `code-review.mjs` (dispatched by `review-toolkit:review-lead`) and `intake-review.mjs` (dispatched by `intake-toolkit:intake-orchestrator` / `decomposition-reviewer` through the sanctioned intake-toolkit → review-toolkit arrow), with the runtime shim and their selftests; the tier alphabet `model-tiering.md` sits at the plugin root beside them. **The Workflow tool does NOT resolve a bare filename against an installed-plugin search path** — measured: `scriptPath: "code-review.mjs"` fails as `Workflow script file not found`, and the plugin cache's own absolute path fails as `must be a script path this tool returned, or a file you can already read`, because the cache is not an added directory on a default install. So the dispatching skill copies the script into the session scratchpad and dispatches that copy, which needs no per-machine `permissions.additionalDirectories` entry (an agent cannot add one — the auto-mode classifier refuses settings edits as self-modification). review-lead reads its own plugin's copy (`$SKILL_DIR/../../workflows/code-review.mjs`). The intake skills search the marketplace root (`$SKILL_DIR/../../../..`) confined to `*/review-toolkit/*` paths, excluding `*/fixtures/*`, and take the highest version; there is no fallback to another plugin. An enabled review-toolkit that predates the move is a doctor FAIL: update all second-shift plugins together.

   **Enforcement (CI).** Two greps over the four toolkits: (a) no `dev-pipeline:` namespace token anywhere; (b) no `dev-pipeline/`-path reference (`dev-pipeline/{workflows,model-tiering}`, `../dev-pipeline/`) in toolkit **content** (every `.md` and `.mjs` outside `scripts/` and `evals/`). Those two directories are excluded from (b): they hold tools and fixtures, not content a skill or agent loads.

   **The sanctioned arrows out of second-shift.** The onboarding micro-plugin resolves
   dev-pipeline's `config-lint.sh` at runtime — via `claude plugin list --json`
   `installPath`, or via the pinned-ref contents API when dev-pipeline isn't installed yet —
   and hands it review-toolkit's `model-tiering.md` resolved the same way; its doctor
   resolves the tools it runs likewise. This is tool resolution by install path, never a
   hard-coded content path, and it is one-directional (no other plugin knows of
   second-shift). **`second-shift` is deliberately NOT in the
   CI grep's `TOOLKITS` list** — its whole job is to reference the other plugins; adding it
   to the grep would break onboard by design. Don't "fix" that.
4. **Tolerant resolution** where runtime namespaces vary (top-level vs plugin-bundled MCP servers): probe every spelling, as `code-review.mjs` does for the three Atlassian namespaces — `select:` silently ignores absent prefixes, so one dispatch serves every registration.
5. **Migration compatibility**: consumer repos must not carry files shadowing plugin-shipped names (the `check-reviewer-references.sh` tripwire); the old `figma-faithful:` namespace is retired in each repo's migration PR, not aliased.
6. **Restart after deleting vendored copies.** The migration deletion (removing repo-local `.claude/skills/*` / `.claude/agents/*` that shadow plugin names) must be followed by a **fresh Claude Code session** before invoking any plugin-namespaced skill. Observed on the first migrated consumer: deleting the vendored skills mid-session invalidated the session's in-memory skill registry — every `Skill(<plugin>:<name>)` invocation returned "Unknown skill" for the rest of that session, while the installed plugins remained fully valid on disk (`claude plugin details <plugin>@second-shift` lists the skills; a fresh session resolves them). There is no in-session reload. Sequence a migration as: enable plugins → delete vendored copies → commit → **restart the session** → run the validation gates (selftests, dry-run ticket) in the new session.
